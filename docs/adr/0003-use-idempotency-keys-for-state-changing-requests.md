# ADR 0003: 상태 변경 요청에 멱등성 키를 사용한다

- 상태: 승인됨(Accepted)
- 결정일: 2026-07-22

## 맥락

클라이언트와 서버 사이의 네트워크 통신은 응답이 도착하지 않거나 시간 초과(Timeout, 정해진 시간 안에 응답을 받지 못한 상태)가 발생할 수 있습니다.

예를 들어 서버가 재화 지급을 성공적으로 끝냈지만, 응답을 보내기 전에 네트워크가 끊기면 클라이언트는 성공 여부를 알 수 없습니다. 클라이언트가 같은 요청을 다시 보내면 재화가 두 번 지급될 위험이 있습니다.

이 문제는 보상 수령, 아이템 구매, 재화 차감처럼 상태를 변경하는 명령에서 특히 중요합니다.

## 결정

상태를 변경하는 API 요청에는 Idempotency Key(멱등성 키, 같은 요청을 한 번만 처리하기 위한 고유 식별값)를 사용합니다.

클라이언트는 요청 하나를 만들 때 UUID(Universally Unique Identifier, 범용 고유 식별자) 형태의 키 하나를 생성하여 요청에 포함합니다. 재시도할 때는 반드시 **같은 키**를 다시 보냅니다.

서버는 다음 원칙으로 처리합니다.

1. 요청의 사용자 ID, API 경로, 멱등성 키를 함께 식별합니다.
2. Redis에서 최근 처리 기록을 먼저 확인합니다.
3. 이미 완료된 키면 게임 규칙을 다시 실행하지 않고, 이전 결과를 반환합니다.
4. 처음 보는 키면 PostgreSQL Transaction 안에서 게임 상태 변경과 멱등성 기록 저장을 함께 처리합니다.
5. PostgreSQL에는 멱등성 키에 대한 `UNIQUE` 제약을 둬서 최종적으로 중복 저장을 막습니다.
6. 성공한 결과는 Redis에 TTL(Time To Live, 데이터가 자동 삭제되기까지의 시간)과 함께 저장해 빠른 재시도 응답에 사용합니다.

## 처리 흐름

```text
클라이언트: 보상 수령 요청 + Idempotency-Key
    ↓
Redis: 처리 완료 기록 확인
    ├─ 있음: 이전 응답 반환, 보상 재지급 없음
    └─ 없음: PostgreSQL Transaction 시작
                 ├─ 보상 지급 또는 재화 변경
                 ├─ 지급 이력 저장
                 └─ 멱등성 키 기록 저장(UNIQUE 제약)
              Transaction 성공
                 ↓
              Redis에 완료 결과와 TTL 저장
                 ↓
              클라이언트에 성공 응답 반환
```

## 선택 이유

멱등성 키는 “같은 HTTP 요청이 두 번 왔는가?”가 아니라 “같은 사용자가 같은 작업을 재시도했는가?”를 구분하는 번호표입니다. 이 번호표가 있으면 서버는 네트워크 재시도와 실제로 새로운 요청을 구분할 수 있습니다.

Redis는 이미 완료된 요청을 빠르게 반환하는 데 적합합니다. 그러나 Redis 기록은 만료되거나 유실될 수 있으므로, 영구 중복 방지의 최종 근거는 PostgreSQL의 Transaction과 `UNIQUE` 제약으로 둡니다.

## 고려한 대안

### 멱등성 키 없이 요청마다 무조건 처리

- 장점: 요청 형식과 서버 코드가 단순합니다.
- 단점: 네트워크 재시도만으로 아이템·재화가 중복 지급될 수 있습니다.

게임 경제에 직접 영향을 주므로 선택하지 않았습니다.

### Redis 기록만으로 중복 처리 방지

- 장점: 구현과 조회가 빠릅니다.
- 단점: Redis 장애, 만료, 저장 실패 뒤에 재시도되면 영구 중복 방지가 보장되지 않습니다.

Redis는 보조 방어선으로만 사용합니다.

### PostgreSQL 기록만으로 중복 처리 방지

- 장점: 최종 정확성은 보장할 수 있습니다.
- 단점: 모든 재시도 요청이 PostgreSQL까지 도달하고, 이전 응답을 빠르게 재사용하기 어렵습니다.

초기에는 가능한 선택이지만, 이 프로젝트에서는 Redis와 PostgreSQL의 역할 분리를 학습하기 위해 두 단계를 함께 사용합니다.

## 구현 세부 원칙

- 키의 유효 범위는 `사용자 ID + API 경로 + 멱등성 키`입니다.
- 같은 키로 다른 요청 본문(Body, 요청 데이터)을 보내면 오류로 처리합니다. 같은 번호표로 다른 작업을 수행하게 해서는 안 됩니다.
- 처리 중인 키가 다시 들어오면 완료될 때까지 기다리게 하거나 `409 Conflict(충돌)` 또는 재시도 가능 응답을 반환하는 정책을 별도로 정합니다.
- Redis TTL은 API 특성에 맞게 정합니다. 포트폴리오 초기 구현에서는 24시간을 기본값으로 둡니다.
- 멱등성 키 기록과 실제 게임 상태 변경은 가능한 한 같은 PostgreSQL Transaction 안에서 저장합니다.

## 결과와 제약

- 상태 변경 API는 멱등성 키를 요구하므로 클라이언트 구현도 이에 맞춰야 합니다.
- 저장해야 할 이전 응답의 범위, 처리 중 요청의 응답 방식, TTL 값은 API별로 구체화해야 합니다.
- 결제처럼 외부 시스템까지 포함된 작업은 추가적인 보상 트랜잭션(Compensating Transaction, 실패한 작업을 반대 작업으로 보정하는 처리) 전략이 필요할 수 있습니다.
