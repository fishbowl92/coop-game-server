# ADR 0001: 게임 엔티티 상태 조정에 Orleans를 사용한다

- 상태: 승인됨(Accepted)
- 결정일: 2026-07-22

## 맥락

협동 게임 서버에서는 플레이어, 파티, 매치처럼 각자 식별자와 상태를 가진 대상이 동시에 요청을 받을 수 있습니다.

예를 들어 한 플레이어가 동시에 재화 획득 요청과 아이템 구매 요청을 보내면, 두 요청이 같은 재화 값을 읽고 수정하면서 결과가 꼬일 수 있습니다. 이를 동시성(Concurrency, 여러 작업이 시간상 겹쳐 실행되는 성질) 문제라고 합니다.

이 프로젝트는 C#과 .NET 환경에서 이러한 상태를 가진 게임 대상을 자연스럽게 표현하고, 이후 여러 서버로 확장할 수 있는 구조를 학습하는 것을 목표로 합니다.

## 결정

상태를 가진 게임 엔티티는 Microsoft Orleans(오를리언스)의 Grain(그레인, 가상 액터)으로 모델링합니다.

- `PlayerGrain`: 플레이어 한 명의 상태와 명령을 담당합니다.
- `PartyGrain`: 파티 한 개의 구성원과 준비 상태를 담당합니다.
- 이후 필요한 경우 `MatchGrain`: 매치 한 개의 진행 상태를 담당합니다.

HTTP(Hypertext Transfer Protocol, 웹 요청·응답 통신 규약) 요청은 API(Application Programming Interface, 프로그램 간 기능 호출 약속) 프로젝트가 받고, API는 해당 Grain에게 작업을 요청합니다. Grain은 게임 규칙을 처리한 뒤 필요한 결과를 API로 돌려줍니다.

PostgreSQL은 계정, 재화, 인벤토리처럼 잃으면 안 되는 영구 데이터의 최종 기준으로 유지합니다. Orleans의 메모리 상태만을 영구 데이터의 유일한 기준으로 사용하지 않습니다.

## 선택 이유

Orleans는 가상 액터 모델을 제공하며, Grain은 식별자를 기준으로 호출되는 상태 보유 단위입니다. 이 방식은 플레이어와 파티처럼 게임에서 자연스럽게 식별되는 대상을 코드 구조에 직접 반영하기 좋습니다.

처음에는 로컬 단일 Silo(사일로, Orleans 서버 실행 단위)로 시작합니다. 이후 여러 Silo로 확장할 때도 Grain 호출 방식은 가능한 한 유지하는 것을 목표로 합니다.

또한 지원 공고의 핵심 기술인 Orleans를 단순히 설치하는 데 그치지 않고, 동시성·상태·영속성의 경계를 고민한 근거를 포트폴리오에 남길 수 있습니다.

## 고려한 대안

### ASP.NET Core 서비스와 직접 작성한 lock

`lock` 또는 `SemaphoreSlim`(세마포 슬림, 비동기 작업 수를 제한하는 동기화 도구)으로 플레이어별 동시성을 직접 제어할 수 있습니다.

- 장점: 시작하기 쉽고 의존성이 적습니다.
- 단점: 플레이어별 잠금 관리, 여러 서버로 확장했을 때의 동기화, 상태 수명 관리를 직접 설계해야 합니다.

작은 단일 서버에는 유효하지만, 이 프로젝트의 학습 목표와 확장 시나리오에는 Orleans가 더 적합하다고 판단했습니다.

### 직접 만든 액터 큐

플레이어 ID별 메시지 큐와 작업자를 직접 구현하는 방법입니다.

- 장점: 내부 동작을 가장 깊게 학습할 수 있습니다.
- 단점: 활성화, 비활성화, 오류 복구, 분산 배치 같은 기반 기능을 모두 직접 구현해야 합니다.

처음부터 프레임워크를 재구현하기보다 Orleans를 사용하고, 필요한 동작은 작은 실험 코드로 별도 학습하기로 했습니다.

## 결과와 제약

- 게임 규칙은 Grain 내부에 두되, HTTP 처리와 데이터 저장 책임은 Grain에 무분별하게 섞지 않습니다.
- Grain이 요청을 한 번에 하나씩 처리한다고 가정해도, 데이터베이스 저장 실패·네트워크 재시도·중복 요청은 별도로 다뤄야 합니다.
- 이 때문에 재화 지급과 구매 같은 변경 작업에는 멱등성(Idempotency, 같은 요청을 여러 번 처리해도 결과가 한 번 처리한 것과 같은 성질) 키 정책을 별도 ADR로 정의합니다.
- Orleans 자체의 구성과 관측 가능성(Observability, 실행 상태를 로그·지표·추적으로 파악하는 능력)도 학습 비용으로 남습니다.
