# 요청 취소와 재시도 원칙

## 목적

HTTP(Hypertext Transfer Protocol, 웹 요청·응답 통신 규약) 클라이언트는 네트워크 문제, 화면 전환, 시간 초과로 연결을 끊을 수 있습니다.
서버는 더 이상 필요하지 않은 작업을 가능한 한 빨리 멈춰 자원을 아끼되, 상태 변경 요청을 무분별하게 재시도해 데이터를 중복 변경해서는 안 됩니다.

이 문서는 Player API의 요청 취소 원칙과 2주차에 구현한 보상 멱등성(Idempotency, 같은 요청을 여러 번 처리해도 결과가 한 번 처리한 것과 같은 성질), 이후 재시도 정책의 기준을 기록합니다.

## 현재 구현

`PlayersController`의 각 비동기 API 메서드는 `CancellationToken`(취소 토큰, 작업을 중단해 달라는 신호)을 매개변수로 받습니다.

- Player 조회는 `SingleOrDefaultAsync(..., cancellationToken)`에 전달합니다.
- Player 생성·닉네임 변경 저장은 `SaveChangesAsync(cancellationToken)`에 전달합니다.

클라이언트 연결이 끊기면 ASP.NET Core는 취소 토큰을 취소 상태로 만들 수 있습니다. EF Core와 Npgsql가 취소를 받을 수 있는 시점이라면 진행 중인 DB 작업도 중단을 시도합니다.

## 취소가 보장하지 않는 것

취소 신호는 “이 작업이 절대로 DB에 반영되지 않았다”는 보장이 아닙니다.

예를 들어 서버가 PostgreSQL에 `UPDATE`를 전송한 직후 클라이언트 연결이 끊기면, DB는 이미 커밋했지만 클라이언트는 응답을 받지 못했을 수 있습니다. 클라이언트가 같은 변경 요청을 단순 재전송하면 처리 결과를 알 수 없고, 보상·재화처럼 민감한 데이터는 중복 변경될 위험이 있습니다.

## 재시도 원칙

### 읽기 요청

프로필 조회처럼 상태를 바꾸지 않는 읽기 요청은, 이후 타임아웃·일시적 장애 정책을 정한 뒤 제한된 횟수의 재시도를 검토할 수 있습니다.

### 상태 변경 요청

플레이어 생성, 닉네임 변경, 재화 지급, 우편 수령처럼 상태를 바꾸는 요청은 현재 서버가 자동 재시도하지 않습니다.

- 단순 네트워크 재시도만으로 같은 작업이 두 번 실행될 수 있습니다.
- DB 오류를 모두 성공으로 바꾸거나, 모든 오류를 재시도하지 않습니다.
- 중복을 안전하게 다루려면 요청 식별자 `requestId`와 DB의 UNIQUE 제약·트랜잭션이 필요합니다.

## 구현된 보상 재시도 안전장치

재화·아이템·우편 보상 요청에는 클라이언트가 만든 `requestId`를 포함합니다.

1. 서버는 `requestId`가 이미 처리됐는지 확인합니다.
2. 처음 요청이면 재화 변경과 감사 로그를 하나의 Transaction(트랜잭션, 여러 DB 변경을 모두 성공하거나 모두 실패하게 묶는 단위)으로 저장합니다.
3. 같은 `requestId`가 재전송되면 보상을 다시 지급하지 않고 이전 결과를 반환합니다.

이 구조는 `RewardService`와 PostgreSQL 통합 테스트에 구현되었습니다. 같은 `requestId` 100개 동시 요청은 보상을 정확히 한 번만 적용하고, 같은 키의 다른 본문은 충돌로 거부하며, 지갑 갱신 실패 시 감사 로그도 함께 Rollback됩니다.

2026-08-13에는 서로 다른 `requestId` 100개가 같은 Player에게 동시에 들어오는 시나리오도 추가했습니다. Player 행을 `SELECT FOR UPDATE`로 잠가 서로 다른 정상 요청의 누적값이 유실되지 않도록 했습니다. 이는 멱등성과 별도의 동시성 제어입니다.

## 현재의 한계

- 프로젝트 수준의 DB 명령 타임아웃 값과 재시도 정책은 아직 설정하지 않았습니다.
- PostgreSQL 장애·지연 상황은 관측성·장애 대응 주차에서 의도적으로 실험합니다.
- 취소 토큰 자체와 DB 명령 취소 시점은 아직 자동 검증하지 않습니다.
- 트랜잭션·동일 requestId 중복·서로 다른 requestId 동시 요청은 PostgreSQL 통합 테스트로 검증합니다.
