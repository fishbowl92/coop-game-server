# 8주차: 재현 가능한 HTTP 부하와 데이터 정합성

기준일: 2026-09-23. 상태: 실험 계약 및 9회 기준 측정 완료. 현재 코드와 이전 학습 문서의 작성 시점을 구분한다.

## 1. 기준과 차이

- 기준 소스: 가이드라인 `d0e3a4e`, 부하 실행기 `fe61f83`, 보고서 `76939f7`. 세 커밋이 2026-09-23 GitHub main에 게시됐고 `76939f7`의 CI가 통과했다.
- 8주차 Notion 노트는 2026-09-07의 f186650 기준이며 전투 명령, Redis 조회, 추적을 미구현으로 설명한다. 이 세 기능은 현재 코드와 7주차 검증에서 확인됐다.
- 노션 대시보드와 로드맵의 완료 상태도 뒤처져 있다. 사용자가 학습 센터의 일괄 갱신을 후속 주차로 미뤘으므로, 8주차 구현은 현재 코드와 이 계약을 기준으로 한다.
- 7주차 로드맵이 요구한 Redis 장애 보고서는 저장소에 없다. 관측성 코드·CI 완료와 보고서 산출물 완료를 분리한다.
- 기존 전체 솔루션 스타일 검사는 과거 파일의 서식 오류로 실패한다. 9주차에 CI 관문으로 넣기 전 기존 기준선을 정리한다.

## 2. 결과와 책임

외부 HTTP 경로 두 개를 시험한다. 진행도 첫 페이지 조회는 API 인증, Orleans PlayerGrain과 캐시 준비 후의 조회 경로를 포함한다. Redis 장애 시 PostgreSQL 대체 경로는 이번 측정에 포함하지 않는다. 여러 게임 방의 유효한 스킬 명령은 API 인증, 연결 자격·순번 검사, Grain 상태 전이, PostgreSQL 저장을 포함한다.

시험 도구는 데이터 준비, 일정한 요청 도착률, 응답 분류, 원시 결과, 시험 후 읽기 전용 정합성 검사만 맡는다. 게임 규칙과 영속성 계약은 변경하지 않는다. 성능 수치와 기능 정확성 테스트의 주장은 별도로 기록한다.

## 3. 고정할 실험 조건

- 대상: 로컬 단일 API·단일 Silo, 시험 전용 PostgreSQL 17·Redis 7 컨테이너.
- 부하 도구: NBomber 6.6.0, .NET 10, 개인 포트폴리오 용도.
- 부하 모형: 매초 일정한 새 요청을 투입하는 개방형 모형. 실행 설정에 초당 요청 수, 측정 시간, HTTP 시간 제한을 남긴다. 준비 단계와 측정 단계의 구분을 기록한다.
- 진행도: 준비된 Player의 첫 페이지를 읽으며, 따뜻한 캐시 시험은 준비 단계에서 같은 첫 페이지를 한 번 조회한다. 실제 적중률은 독립 계측하지 않았다. 차가운 캐시와 Redis 중단은 별도 시험이며 따뜻한 캐시 수치에 섞지 않는다.
- 전투: 네 Player가 소속된 방을 매칭으로 준비하고 모두 접속한 뒤 시작한다. 방마다 연결 ID·세대, Player별 명령 순번과 스킬 재사용 대기시간을 지킨다. 필요한 방 수를 본 측정 요청 수보다 넉넉히 계산한다. 공격 예열은 하지 않아 첫 공격 지연도 측정에 포함한다. 방 완료·거부 응답은 유효 처리량에서 제외한다.
- 준비 요청과 서버 시작·마이그레이션 시간은 측정에서 제외한다. 매 반복은 같은 데이터 수와 새 시험 데이터베이스에서 시작한다.
- 로컬 시험 목표: 준비된 낮은 부하에서 업무 성공률 100%, 예상치 못한 HTTP 오류 0건, p95 2초 이내. 이 값은 운영 SLO가 아니라 시험 도구와 환경의 정상 동작 확인 기준이다.
- Before의 3회는 같은 커밋·환경·설정으로 재실행한다. 병목이 증명되어 코드를 바꾸면 새 커밋에서 같은 환경·설정으로 After 3회를 수집한다. 이번 9회는 기준을 충족했고 지속 병목이 확인되지 않아 After 코드 변경을 만들지 않았다.

## 4. 실패와 정합성

- 성공 응답, 예상된 업무 거부, HTTP·네트워크 오류를 분리한다. 이번 시나리오는 멱등 재생을 투입하지 않고 재생 응답은 유효 신규 명령에서 제외한다. 빠른 4xx를 성공 처리량에 합치지 않는다.
- 요청 ID는 새 명령마다 새 값을 쓰고, 명시적 재전송만 같은 값과 본문을 사용한다.
- 시험 뒤 재화·인벤토리의 음수, 방 참가자 수, 명령 순번, 캐시 응답과 DB 원본 일치 여부를 읽기 전용으로 확인한다. 이번 스킬 시나리오는 완료 전 상태까지만 측정하므로 보상·결과 행이 없어야 한다. 완료 후 중복 지급과 결과 전달은 이 부하 시험의 검증 범위 밖임을 결과에 명시한다.
- 시험용 비밀번호·JWT·연결 문자열은 결과와 로그에 쓰지 않는다. 실험 조건과 커밋·버전·머신 자원만 기록한다.
- 부하 수치와 병목 결론은 이 PC의 단일 Silo·시험용 저장소에만 적용한다.

## 5. 구현·검증·커밋 경계

1. 시험 전용 Compose와 한 명령 실행 스크립트, 별도 LoadTests 실행 프로젝트를 만든다.
2. 준비 데이터와 두 시나리오가 실제 HTTP 성공을 반환하는지 낮은 부하로 확인한다.
3. 적정 단계에서 Before를 각각 3회 수집하고 원시 결과·설정·환경을 보존한다. [8주차 측정 보고서](../performance/week-08/README.md)에 기록했다.
4. Trace·Metric·SQL 근거로 병목 하나가 확인되면 한 변경만 별도 커밋으로 적용한다. 확인되지 않으면 변경 없이 결과를 기록한다.
5. 부하 뒤 정합성 검사, Release 솔루션 빌드와 전체 단위·통합 테스트를 실행한다.
6. 구현, 성능 결과, 문서·인계 기록을 리뷰 가능한 커밋으로 나눈다. GitHub 게시와 동일 커밋 CI 결과는 별도 상태로 보고한다.
