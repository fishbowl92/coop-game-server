# ADR 0002: PostgreSQL과 Redis의 책임을 분리한다

- 상태: 승인됨(Accepted)
- 결정일: 2026-07-22

## 현재 구현 상태 — 2026-08-13

- PostgreSQL은 Player·지갑·인벤토리·보상 감사 로그의 최종 저장소로 실제 사용 중입니다.
- 보상 감사 로그·지갑·인벤토리는 하나의 Transaction으로 변경됩니다.
- Redis 컨테이너는 로컬 환경에 준비되어 있지만 애플리케이션은 아직 Redis에 연결하지 않습니다.
- 아래 Redis 캐시·TTL·빠른 멱등성 조회 흐름은 **5주차 목표 설계**이며 현재 완료 기능이 아닙니다.

## 맥락

협동 게임 서버는 정확성이 중요한 데이터와 빠른 응답이 중요한 데이터를 함께 다룹니다.

예를 들어 플레이어의 보유 재화와 인벤토리는 잘못되거나 사라지면 안 됩니다. 반면 잠깐 유지되는 로그인 세션, 자주 읽는 조회 결과, 요청 중복 방지 기록은 사라져도 원본 데이터 또는 클라이언트 요청을 바탕으로 다시 만들 수 있습니다.

한 저장소에 모든 책임을 넣으면 각 데이터의 특성에 맞는 보관·조회 방식을 선택하기 어려워집니다.

## 결정

PostgreSQL(포스트그레스큐엘)은 영구 데이터의 최종 기준(Source of Truth, 데이터의 공식 원본)으로 사용합니다. Redis(REmote DIctionary Server, 원격 딕셔너리 서버)는 빠르게 접근할 수 있는 단기 데이터와 보조 기능에 사용합니다.

### PostgreSQL 책임

- 플레이어 계정과 프로필
- 재화 잔액과 재화 변동 이력
- 인벤토리와 소유 아이템
- 구매·보상 지급처럼 나중에 검증해야 하는 결과
- 여러 변경을 함께 성공 또는 실패시켜야 하는 작업

PostgreSQL의 Transaction(트랜잭션, 여러 데이터 변경을 하나의 작업으로 묶는 기능)을 사용해 재화 차감과 아이템 지급이 함께 성공하거나 함께 실패하도록 처리합니다.

### Redis 책임

- 로그인 세션 또는 짧은 수명의 인증 정보
- 멱등성 키의 처리 완료 기록
- 자주 조회되는 읽기 전용 데이터의 Cache(캐시, 원본 대신 빠르게 재사용하는 임시 저장값)
- 요청 횟수 제한이나 짧은 시간의 카운터

Redis에 저장하는 키에는 가능한 한 TTL(Time To Live, 데이터가 자동 삭제되기까지의 남은 시간)을 설정합니다. 예를 들어 멱등성 키는 24시간 뒤 자동 삭제되도록 둘 수 있습니다.

## 선택 이유

PostgreSQL은 관계형 데이터베이스로서 계정·재화·인벤토리처럼 서로 연결된 데이터를 질의하고 Transaction으로 정확하게 변경하기 적합합니다.

Redis는 메모리 기반 데이터 저장소로, 키를 기준으로 짧은 수명의 데이터를 빠르게 읽고 쓰는 데 적합합니다. 캐시가 사라져도 PostgreSQL의 원본에서 다시 채울 수 있도록 설계하면, Redis 장애가 영구 데이터 손실로 이어지지 않습니다.

## 최종 목표 데이터 흐름 예시

```text
플레이어의 프로필 조회
    ↓
Redis 캐시 확인
    ├─ 값 있음: 캐시 값을 즉시 반환
    └─ 값 없음: PostgreSQL에서 조회 → Redis에 짧게 저장 → 반환

재화 지급 요청
    ↓
Redis에서 멱등성 키 중복 확인
    ↓
PostgreSQL Transaction으로 재화와 이력 저장
    ↓
필요하면 관련 캐시를 삭제 또는 갱신
```

## 고려한 대안

### PostgreSQL만 사용

- 장점: 운영 대상이 하나라 단순합니다.
- 단점: 세션, 요청 중복 기록, 빈번한 조회까지 모두 데이터베이스에 의존하게 됩니다.

초기 구현에서는 정확성과 단순성을 우선해 PostgreSQL만 사용하는 단계를 선택했습니다. Redis는 캐시의 필요성과 장애 시 대체 정책을 측정할 수 있는 5주차에 추가합니다. 최종 책임 분리 결정은 그대로 유지합니다.

### Redis만 사용

- 장점: 단순한 키 조회는 빠릅니다.
- 단점: 재화·인벤토리처럼 정확한 영구 기록과 복잡한 관계를 다루는 최종 기준으로는 부적합합니다.

Redis는 영속화 기능을 제공할 수 있지만, 이 프로젝트에서는 영구 데이터의 원본 책임을 PostgreSQL에 둡니다.

## 결과와 제약

- 쓰기 작업의 성공 기준은 PostgreSQL 저장 성공입니다.
- 캐시 값은 원본보다 오래될 수 있으므로, 변경 직후 캐시 삭제 또는 갱신 정책을 명시해야 합니다.
- Redis 장애 시에는 캐시를 사용하지 않고 PostgreSQL에서 조회하는 방식으로 기능을 유지해야 합니다.
- 두 저장소에 같은 데이터를 동시에 기록해야 한다면, 실패 순서와 복구 전략을 별도로 설계해야 합니다.
